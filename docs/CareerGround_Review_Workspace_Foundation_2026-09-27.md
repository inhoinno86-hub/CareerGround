# Temporary Claim review workspace (synthetic only)

Migration `20260927_0007` adds temporary `profiling_drafts`, `profiling_review_batches` and `profiling_review_items` with composite owner/session/scope foreign keys. A batch has at most five positions and nullable, explicit item decisions; no database default can mean approval. All rows remain tied to a profiling session and expire with that workspace. This is E02-T01/T02 storage progress and E03-T03 preparation only, not canonical Claim promotion.

`propose_verbatim_draft` accepts only a substring of one explicitly submitted input in the same account and session. It does not generate or infer a new fact. `ClaimReviewPreparation.prepare` locks the owned session/profile and drafts, requires one experience scope and the current profile version, checks the source hash, then snapshots exact wording, source input ID, type and scope. The HMAC digest binds those values plus account, session, profile, version, review purpose and expiry. `get` returns the original snapshot only and rejects tampering, expiry or wrong-account access. It does not change the canonical profile.

The local synthetic-only MCP `prepare_claim_review` wrapper requires `career.profile.write`. Its domain command selects all current `DRAFT` rows from one owned scope in a fixed order and rejects an empty scope or more than five drafts; it never silently selects only the first five. A bounded idempotency key returns the same unexpired batch and digest on replay, while reuse for another scope is rejected. The output contains the exact review snapshot and no approval decision. A public review route and real-user approval issuer do not exist yet.

An isolated synthetic browser app factory now renders that exact prepared snapshot as escaped HTML. Each item starts with no selected decision, and submission requires a choice for every item plus an explicit confirmation checkbox. The domain presentation service signs a three-minute token bound to a non-secret opaque browser-session binding, account, batch, item IDs, base version and review digest. It verifies the token before constructing `VerifiedReviewApproval`; `submit_synthetic_review` still rechecks the exact stored batch, source, profile version and ownership within the caller transaction. The browser app has no public entrypoint and requires a caller-supplied trusted session adapter. Its first synthetic test adapter uses an in-memory cookie map.

An optional Auth0 session adapter now calls the installed SDK's `require_session` on every request, maps its verified `(issuer, subject)` to an `ACTIVE` account through a fresh database session, and derives a non-secret HMAC browser binding from the Auth0 session cookie chunks. Neither the raw cookie nor bearer token is put into the signed form payload. Malformed chunk names, a missing session, an unlinked/disabled account and a cookie rotated between display and submission fail closed. SDK `Set-Cookie` headers are preserved by the isolated browser factory. The bridge was tested with a fake verified-session reader and synthetic accounts only; no live Auth0 tenant, real user, public route or operational database was connected. Real-user display evidence, production session/CSRF integration, high-impact review presentation and deployment remain separate gates.

The isolated browser factory also has a read-only profiling status page. The owner-scoped domain summary shows effective session status, base/current profile versions, current protocol state, temporary draft counts, retention expiry and up to ten prepared review links. It does not deliver a question, extend retention, mutate the profile or return an input body or conversation history. An outdated profile version shows a blocked protocol state; each linked review still performs its own digest/version check. This is a synthetic navigation foundation, not a complete profiling journey.

The same synthetic factory now has an explicit `ADD_EXPERIENCE` start form. It shows the active profile version, existing unexpired sessions, task-only collection notice and 90-day temporary retention before the user checks confirmation. A short signed token binds the active account, opaque browser session, profile version and random idempotency key. Replaying one submitted form returns the same new session without extending retention; missing confirmation, a different browser session or a changed profile version creates no session. Login, installation or GET never starts profiling. This form has no public route, real input collection or live identity connection.

An explicit single-input form is available in the same isolated synthetic app for an active owned session. It accepts one user-written `USER_STATEMENT` of at most 20,000 characters after an explicit checkbox; the signed token binds account, browser session, task session, base profile version and an idempotency key. The exact same retry returns the stored input, while altered content, another browser session, a paused/stale session, extra form fields or a missing confirmation are rejected. Neither the status page nor its links return the input body. These browser forms use a shared HMAC envelope with strict token purposes and field sets. Selected chat/document excerpts, actual ChatGPT context access and live user collection remain outside this factory.

The active-session screen also offers a separate explicit `CORRECTION` form. Its signed token fixes the content kind, so an ordinary experience-input token cannot be submitted as a correction or vice versa. The page explains that a correction starts a new question cycle, expires prepared review batches and returns temporary drafts to `EDIT_REQUIRED`. Replaying the same correction does not start another cycle. No Claim or canonical profile version is changed by this form.

The synthetic session status page now offers an explicit pause or resume form. A short signed token binds the action, account, browser session, task session, profile version, and last activity timestamp. The POST accepts only that form's exact action and confirmation. Pausing leaves activity and retention unchanged; resuming a paused session extends the 90-day window once as deliberate activity. A replayed resume token, later input, another browser session, changed profile version, expired session or altered action cannot extend it again. GET remains read-only and no operational route is mounted.

A separate owner-scoped synthetic draft list displays up to 50 unexpired, exact proposed phrases with scope, type and status. It escapes the text, clearly labels it unconfirmed, omits raw input bodies and does not deliver a question, approve a Claim, update the profile or refresh retention. It denies foreign, deleting and expired sessions. A larger list is explicitly marked as truncated; paging and draft editing remain future work.

The synthetic browser now links each visible `DRAFT` scope of one to five items to an explicit review-preparation form. GET shows the exact escaped wording and issues a three-minute token bound to the active account, opaque browser session, task session, scope, base profile version, and a digest of the displayed draft IDs, source refs, types, hashes and text. A confirmed POST uses the existing domain `prepare_for_scope` command, compares the newly stored snapshot with the display digest, and redirects to the exact review form. It returns the same batch on a token retry without creating a second batch; a changed draft/source/profile, foreign session, altered scope, missing confirmation or six-item scope creates no batch. Preparation still does not approve a fact or change the canonical profile. The draft list omits scope links when truncated at 50 items so it does not imply a complete display.

The approved separate Claim use review is described in [Claim Use Review Foundation](CareerGround_Claim_Use_Review_Foundation_2026-09-29.md). A fact `ACCEPT` still leaves R1 use blocked until that separate explicit check appends an eligible assessment.

For an explicitly submitted `USER_STATEMENT` containing one to five lines beginning with `- ` or `* `, the synthetic browser offers a separate draft selection page immediately after input. It displays only those exact source slices, requires a user-entered experience scope and confirmation, and labels them `CONTRIBUTION` candidates rather than verified facts. A three-minute token binds the owner, browser session, input ID/hash, protocol cycle and profile version. The domain stores a stable draft set once per source; retry returns the same rows, while a different scope, changed source, correction cycle or altered browser session is rejected. Other input formats simply return to session status. This deterministic path calls no AI provider and never promotes a Claim on its own.

The isolated browser factory renders generic Korean error pages for form/ownership conflicts with a start-screen recovery link where useful. Error pages have `role=alert` and no-store/security headers; they do not echo submitted text, signed form tokens or server exception details. Native labels, required controls and fieldsets support keyboard use in the current simple forms, but a full accessibility audit and end-to-end user journey remain unfinished.

The retention worker removes these temporary rows with the expired session/input. Deletion preview includes their IDs; confirmation blocks the account/profile and queues their local cleanup. Quarantined restore replay purges them before an old synthetic copy is considered ready. Selected canonical Evidence is not stored in these tables and must get a separate retention and erasure path when the Graph schema exists.

Synthetic tests cover one-to-five item limits, mixed-scope rejection, no inferred Claim from unsupported text, stale source/profile version, digest tampering, cross-account foreign keys, deletion impact and expiry/restore cleanup. PostgreSQL migration/check for `0007` passed on an isolated local `_test` database. The internal synthetic submission and Graph storage now exist in [the canonical Graph foundation](CareerGround_Canonical_Graph_Foundation_2026-09-27.md); a real approval issuer and public route do not. `ready_to_execute=false` remains the deletion boundary.
