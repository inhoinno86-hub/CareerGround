# JD and resume artifact foundation (synthetic only)

Migration `20260927_0010` adds owner-scoped `job_descriptions`, `jd_requirements`, `requirement_claim_maps`, `artifacts`, `artifact_units`, and `artifact_claim_links`. Composite foreign keys keep each requirement, Claim link, artifact unit and JD in one account/profile. An artifact also has a database foreign key to the exact archived profile version used to create it. Resume text and JD versions have unique per-profile version numbers.

The internal `record_pasted_jd_analysis` path accepts only caller-supplied pasted JD text and one to 50 exact, nonoverlapping spans. It stores the source hash and length plus those excerpts and offsets, without a separate raw-source column; a caller could select a span covering the whole source, so a future UI must explain and bound that choice. It does not classify requirements, follow instructions found in the JD, contact a model/provider, or change the Career Graph. Every stored requirement has type `UNCLASSIFIED`; a later analysis and review path must classify it. `get_jd_analysis` reads only an active account/profile's exact stored version. The function has a local synthetic-only MCP wrapper, but no public web/MCP entrypoint.

The local MCP wrapper requires `career.artifact.read`, validates the active account at the HTTP boundary, and checks the same scope again at the tool. The existing profile read tools still require `career.profile.read`; having either token alone does not grant the other tool family. It requires an exact archived profile version and returns stored excerpts, offsets, source hash/length, recorded potential Claim links, gap status and whether the version is stale. Foreign, missing, unarchived and deleting JD requests share `found=false`. Gap status describes recorded links only; semantic coverage, Evidence strength explanations, requirement classification and a production-safe entrypoint remain unfinished.

The internal `link_jd_requirement_to_claim` path now records an explicit caller-selected requirement/Claim pair for the exact current archived profile version. It rejects another owner, stale/missing archive, missing review or supporting Evidence, non-consistent or restricted assessment, contradiction, and same-scope `NOT_TRUE`/`DO_NOT_USE` constraints. It stores only `POTENTIAL` relevance and leaves Claim status, assessment and profile version unchanged. It does not infer semantic relevance from JD text. `get_jd_mapping` shows recorded potential links or `NO_ELIGIBLE_LINK_RECORDED` gaps for an exact version, with a stale flag when the profile has advanced. A gap means no eligible link was recorded, not that the user lacks the skill. The mapping table has a composite foreign key to that exact archive version.

The internal `generate_resume_draft` path accepts 1–5 explicitly selected, eligible Claims already linked to that JD and exact current profile version. It copies each Claim's exact canonical text into one `R1` resume bullet, creates a `REVIEW_REQUIRED` artifact and an owner-scoped Claim link, and leaves the Graph unchanged. `get_resume_trace` rechecks exact archive, current Claim text/status, JD link, eligibility and supporting Evidence; it returns selected excerpt IDs/text and original input references. Tampered wording and wrong-owner reads fail closed. No model writes new wording here. A separate [R1 wording review and in-memory export foundation](CareerGround_Resume_Wording_Foundation_2026-09-27.md) now exists; R2/R3 review, download resources and public routes remain future work. No actual JD, resume, user account, object store, or operational service is connected.

The owner-approved synthetic [separate Claim use review](CareerGround_Claim_Use_Review_Foundation_2026-09-29.md) can now create an eligible `CONSISTENT`/`ALLOWED` assessment after fact review, selected support and boundary checks. The downstream JD link and R1 export were exercised with that path in a local synthetic test. This does not classify a JD requirement or make a semantic fit judgment.

The local synthetic-only product MCP factory also exposes the existing `get_resume_trace` read under `career.artifact.read`. It returns exact R1 unit text, Claim IDs, selected Evidence IDs/excerpts and original input references; it does not return the full JD or profiling input. Ineligible, tampered, foreign, missing or deleting artifacts all fail closed with `found=false`. This is not a public product entrypoint or a wording-approval route.

The isolated synthetic browser factory now includes a bounded resume artifact list and an exact trace page. The list contains only active-owner draft metadata; each trace read separately rechecks archived profile version, Claim eligibility, wording and Evidence through the existing domain command. The page escapes every displayed phrase and source reference, labels stale profile versions and review status, and never returns the full JD or temporary profiling input. Foreign and tampered artifacts receive 404. This factory is not mounted in the product web app and performs no wording approval or export.

The same isolated factory has a bounded active-owner JD list and exact stored-excerpt page. It uses the existing owner-checked `get_jd_analysis` read and shows only selected spans and offsets; the unselected JD text is not stored or returned. It labels the output as neither automatic requirement classification nor a fit judgment. Foreign IDs receive 404. No live JD collection or provider analysis is connected.

The synthetic browser can now accept an explicitly pasted set of one to five JD requirement bullets from an active owner. Each line must start with `- ` or `* `; only the exact text after those markers is stored as an `UNCLASSIFIED` excerpt with offsets, plus a source hash and length. A ten-minute signed form binds the account, opaque browser session and current profile version, and the POST requires a confirmation checkbox. A repeated identical submission returns the existing JD version; changed profile version, another browser session, prose or an extra form field is rejected. The app factory still has no public mount, external JD fetch, AI interpretation or operational data connection.

When that owner has an empty version-zero profile, the JD submission now creates its exact empty canonical archive in the same transaction. The subsequent mapping page shows no recorded eligible link, and the R1 draft page explains that no Claim can be selected; it renders no submission form. This allows a document-free empty path without inventing a Claim or changing the profile version.

The isolated browser factory also has read-only exact-version canonical profile and Claim evidence pages. The profile page shows archived active Claim text, confirmation/consistency/usage status, and a link to each Claim's selected evidence. The Claim page shows the same archived version's source references and applicable scope constraints. Both reuse the owner-checked Graph projections, escape all text, return no-store pages, and deny a foreign, missing or erased version. The pages distinguish user confirmation from external verification and do not expose entire temporary input bodies.

For an explicitly requested archived profile version, a separate synthetic page renders the recorded JD requirement to Claim links and gap markers from `get_jd_mapping`. An R1 resume trace links to its exact JD/profile-version mapping. The page labels all links as potential, marks stale profile versions and states that a missing link does not prove a skill gap. Foreign or nonexistent archive versions receive 404; no semantic matching is inferred.

The isolated browser now links a saved JD requirement to a current eligible Claim only after showing both exact phrases and selected supporting excerpts. The owner chooses the pair and checks a separate confirmation box. A three-minute signed form binds account, opaque browser session, JD, requirement, Claim, profile version, and display digest; submission locks the owner/profile, checks the live canonical Graph against its exact archive, then calls the existing `POTENTIAL` mapping command. Foreign sessions, extra form fields, source changes, stale profile versions, and ineligible Claims fail closed. Repeating the same submission returns the one existing mapping. The JD excerpt page links to the mapping view; the view shows eligible candidate phrases without assigning relevance automatically.

From recorded links, the owner can select one to five exact eligible Claim phrases for an R1 draft. A separate three-minute signed form binds the candidate set and current version. The POST rechecks the mapping, archived/live Graph and eligibility, then copies the selected canonical phrases into a `REVIEW_REQUIRED` draft. A stable form nonce gives repeated identical submissions one artifact; a changed selection cannot reuse that artifact ID. The draft opens its existing trace and later wording-review path. No AI rewriting, requirement classification, R2/R3 claim, employer transmission or public app mount was added.
