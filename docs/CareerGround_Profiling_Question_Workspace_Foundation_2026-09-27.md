# Profiling question workspace foundation (synthetic only)

`20260927_0013` adds temporary `profiling_protocol_steps`. Each row is scoped to one account, explicit profiling session and Protocol v1 state. The row records at most two delivered questions, idempotency keys, one structured observation and an optional source input from that same session. It contains no copied input body. The same 90-day session expiry, local deletion preview/work, and quarantined restore cleanup apply through composite foreign keys and cascading deletion.

The isolated synthetic browser factory now shows a read-only list of all 13 current-cycle states, question counts and observation statuses. It does not reveal source input IDs, reasons or answer text; opening the page does not count a delivery, interpret an answer or extend retention. A correction starts a new cycle, so old-cycle delivery counts do not appear. Foreign, expired, deleting and profile-version-stale sessions are denied. No actual question/answer interaction or automated observation is wired to this page.

`plan_next_question` is deterministic and does not interpret source text. A trusted internal caller must record each question delivery and provide structured observations. `UNKNOWN` requires both question attempts. A required unknown or unresolved conflict blocks advancement; an optional unknown retains its reason in the temporary row. Recording a question or observation does not refresh the profiling session's activity or retention clock and does not change the canonical profile version.

The planner cannot verify Protocol v1 §7's exact review checklist, so it does not issue `COMPLETE`, even when every question has a sourced observation. It cannot approve a Claim or authorize publication. There is no AI adapter, public API, live collection, or real user data path. Natural language atomicity and truth are outside this deterministic layer.

`20260927_0014` adds a protocol cycle to the temporary session, input and question rows. An explicit `CORRECTION` input starts a new cycle once per idempotency key, expires prepared review batches and returns pending drafts to `EDIT_REQUIRED`. Earlier questions remain available only as temporary historical rows until session erasure; their delivery keys and source inputs cannot satisfy the new cycle. New drafts require an input from the current cycle and a new exact review. This is deliberately conservative across the whole session because no trusted scope mapping exists yet. It does not revise already promoted canonical Claims; that requires the separate contradiction and boundary review paths.

The offline draft extraction helper accepts only one to five exact, nonoverlapping, single-line character spans from one explicit source input. It can locate spans in user-formatted bullet lines, or validate ranges proposed by a future AI adapter. The untrusted adapter output contract accepts only a `spans` list of `start`/`end` integer pairs and rejects every extra field, including proposed wording, ownership, Claim type and approval. Scope and Claim type come from the trusted caller. Parsed candidates carry `UNVERIFIED` atomicity in memory, and saved items remain temporary `DRAFT` rows; no text interpretation, Claim approval, provider call or canonical write occurs. A compound bullet remains one unverified candidate for later human review. Provider choice, data-handling terms and the live AI connection remain open gates.

Local SQLite tests cover owner scope, source linkage, replay, pause/resume, unknown budget, correction re-entry, pending review invalidation, exact-span extraction, strict adapter output parsing, expiry and synthetic deletion. PostgreSQL 17.11 accepted `0013` and `0014`, reported no Alembic schema drift, and passed each migration's downgrade/re-upgrade on an empty synthetic database. Before the strict parser addition, the full suite passed 175 tests without skips, including the PostgreSQL concurrent delivery lock check; all 34 product tables were empty afterward. A local-only temporary forwarder was used because this host's Docker loopback proxy accepted TCP but closed PostgreSQL connections; direct container PostgreSQL responded normally.
