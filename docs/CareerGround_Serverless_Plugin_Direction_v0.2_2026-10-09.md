## 1. 제품 방향

CareerGround는 ChatGPT 플러그인을 통해 개인의 경력을 정리하고, 기본 이력서를 완성하고, JD를 추천받아 지원 목적에 맞는 이력서를 작성하는 도구로 개발한다. 작성 과정의 이력과 필요한 근거를 함께 내보내어 별도로 개발할 모의 면접 앱에서 활용한다.

이력서 플러그인의 필수 경로에서 CareerGround 자체 서버, 상시 실행 프로세스, MCP 연결, 자체 DB, Auth0 로그인과 별도 관리 웹을 제외한다. 공통 업무 규칙과 템플릿은 스킬 플러그인에 넣고, 개인 자료는 사용자가 선택한 ChatGPT 프로젝트와 파일에 둔다. 경력 내용이 플러그인 배포 ZIP에 포함되어서는 안 된다.

이 문서에서 '서버 없음'은 **사용자가 CareerGround 이력서 플러그인을 위해 별도 서버를 실행·운영하지 않는다**는 뜻이다. ChatGPT는 OpenAI 서비스이며, 향후 모의 면접 앱의 모델·음성 실행 방식까지 서버가 필요 없다고 확정하는 것은 아니다.

### 1.1 사용자 요구와 검토 제안의 구분

아래 요구 표와 제안 설명은 최초 방향 정리의 기록이다. 2026-10-09 승인 후의 확정 설계와
현재 구현 상태는 [신규 계약](serverless_plugin_contract_v1.md)과 실행 결과를 따른다.

| ID | 요청에서 확정된 방향 | 문서 반영 |
| --- | --- | --- |
| R01 | 개인이 운영하는 CareerGround 서버를 배제 | 스킬만 포함하는 플러그인이 기본 제품 경로 |
| R02 | 개인의 기본 resume 완성 | 경력 정리 → 사실·사용 검토 → 기본 이력서 |
| R03 | JD 추천 | ChatGPT 검색과 사용자 제공 JD를 활용 |
| R04 | 특정 JD에 맞는 resume 업데이트 | 요구사항 대응, 근거 공백과 변경 내역 표시 |
| R05 | 진행 history와 증거자료 보존·전달 | 작업 기록, 버전, 출처와 선택 자료의 파일 전달 |
| R06 | 개발할 앱에서 모의 면접으로 연결 | 고정 버전의 파일 가져오기 계약과 결과 복귀 |
| R07 | 프로젝트 내 사용 유도와 이유 안내 | 첫 사용 안내, 사용자 준비 확인, 이동 후 재개 |
| R08 | 방향·목표와 단계별 작업 문서 검토 후 지시 | 이번 변경은 문서만 작성; 구현·설치·배포는 미수행 |

다음 항목은 이 문서의 **권장 설계안**이며 사용자 검토 후 작업 기준으로 확정한다: JSON을 구조화된 기준 파일로 사용, Markdown을 검토·이력서 형식으로 사용, 초기 면접 전달을 수동 파일 가져오기로 구현, 프로젝트 준비 전 본 경력 작업을 보류, 플러그인과 면접 앱의 출시 범위 분리. 세부 필드와 UI는 1·2단계에서 계약으로 정한다.

### 1.2 기존 문서와의 관계

기존 서버 중심 [제품 정책](CareerGround_Product_Policy_Proposal_v0.1_2026-09-22.md), [기능 명세](plugin_functional_spec_v1.md), [아키텍처](architecture_v1.md), [면접 패키지 v1](interview_package_schema_v1.json)은 당시 승인된 설계와 검증 기록으로 보존한다. 이 문서는 그 기록을 수정하거나 기존 승인·시험 결과의 의미를 바꾸지 않는다.

신규 구현을 지시받으면 이 문서와 새 계약을 기준으로 서버 없는 제품을 개발한다. 기존 문서의 서버 승인·보관기간·서명 보장을 신규 제품에 그대로 적용하지 않는다. 기존 서버 코드를 삭제하거나 기존 DB·OAuth 연결·비공개 플러그인 등록을 변경하는 것은 이번 문서 작성 범위에 포함하지 않는다.

| 목표 | 사용자에게 제공할 결과 | 완료 판단 |

| G02 기본 이력서 | JD가 없어도 사용할 수 있는 기본 resume | 확인된 경력에 연결된 문장과 검토 결과 제공 |
| G03 JD 탐색 | 희망 조건에 맞는 공고 후보와 추천 이유 | 원문 링크·조회일·확인 범위·부족한 조건 표시 |

| G05 이어서 사용 | 최신 경력 자료, 작업 이력과 버전 재사용 | 새 대화에서 선택한 기준 파일로 복귀 시험 |
| G06 면접 준비 전달 | 선택 JD·resume·근거·이력을 담은 패키지 | 앱의 참조 가져오기 검사에서 연결·버전 확인 |
| G07 면접 결과 복귀 | 피드백과 새 사실 후보의 검토 자료 | 사용자 확인 전 기준 경력·resume를 변경하지 않음 |

G01–G06이 이력서 플러그인의 첫 완성 범위다. G06의 초기 검증은 실제 음성 앱 대신 로컬 참조 가져오기 검사로 할 수 있다. G07은 결과 파일 계약을 먼저 준비하고, 실제 앱을 개발한 뒤 전체 왕복을 검증한다. 플러그인 완료와 면접 앱 완료는 따로 보고한다.

## 3. 실행 구조

```text
사용자의 ChatGPT 프로젝트
  ├─ CareerGround 스킬 플러그인: 절차·질문·작성 규칙·템플릿
  ├─ 사용자 선택 자료: 최신 경력 파일·근거·JD·이력서·작업 이력
  └─ ChatGPT 기본 기능: 대화·검색·파일 생성(제공 환경에 따라 사용)
         ↓ 사용자가 범위 확인 후 다운로드
  면접 전달 파일과 선택 증거자료
         ↓ 사용자가 면접 앱에서 가져오기
  모의 면접 → 결과 파일 → 프로젝트에서 재검토
```

플러그인은 전용 저장소가 아니다. 사용자 계정의 모든 대화, 모든 프로젝트나 비공개 자료를 임의로 조회하지 않는다. 같은 프로젝트 안에서도 현재 접근 가능한 파일과 사용자가 선택한 버전을 확인한다. 프로젝트 소속만으로 최신본·모든 과거 내용·저장 완료가 보장된다고 설명하지 않는다.

프로젝트 밖 실행을 차단하는 플랫폼 기능은 약속하지 않는다. 스킬 지침과 사용자 확인을 통한 흐름이며, 모델의 지침 준수와 파일 이용 가능성은 실제 설치 환경에서 평가해야 한다.

## 4. 프로젝트 시작·이동·재개 흐름

### 4.1 프로젝트를 사용하는 이유

1. 확인한 경력과 증거를 여러 JD 작업에서 재사용할 수 있다.
2. 기본 이력서와 JD별 수정본, 선택·수정·확인 이력을 한 곳에서 관리하기 쉽다.
3. 새 대화에서 기준 자료를 다시 선택해 이어갈 수 있다.
4. 면접 앱으로 전달할 resume·JD·근거의 버전을 맞추기 쉽다.

프로젝트는 자료를 모으는 작업 공간이다. 자동 DB, 전 대화 기억 보장, 외부 사실 검증, 자동 삭제 동기화를 제공하는 것으로 소개하지 않는다.

### 4.2 첫 실행 안내 문구

> CareerGround는 전용 ChatGPT 프로젝트에서 사용해 주세요. 프로젝트에 확인한 경력 자료와 증거, 기본 이력서, JD별 수정본과 작업 이력을 모아 두면 새로운 JD에서도 자료를 재사용하고, 다음 대화에서 작업을 이어가며, 모의 면접 앱에 같은 버전의 자료를 전달하기가 쉬워집니다.
>
> 현재 대화가 CareerGround용 프로젝트 안에서 시작되었나요? 프로젝트 밖이거나 잘 모르겠다면, 먼저 기존 프로젝트로 이 대화를 이동하거나 새 프로젝트를 만든 뒤 그 안에서 CareerGround를 실행해 주세요. 이동이 어려우면 다음 대화에 붙여 넣을 작업 요약을 제공할 수 있습니다.
>
> 준비가 끝나면 “프로젝트에서 준비됐어”라고 알려주세요. 사용할 최신 경력 자료와 이력서를 확인한 뒤 작업을 시작하겠습니다. 프로젝트를 만드는 것만으로 모든 자료가 자동 저장되거나 최신본이 선택되는 것은 아닙니다.

### 4.3 진행 규칙

| 상황 | 동작 | 하지 않을 주장 |
| --- | --- | --- |
| 새 대화에서 첫 사용, 소속을 확인할 수 없음 | 안내와 프로젝트 여부 확인을 한 번 제공 | 프로젝트 밖이라고 자동 판정 |
| 사용자에게 프로젝트 밖임을 확인받음 | 사용자 UI 조작으로 생성·이동하거나 프로젝트에서 새 대화하도록 안내 | 생성·이동을 수행했다고 보고 |
| 준비 전 | 설치·사용 설명과 이동용 요약만 제공 | 실제 경력·민감한 증거를 먼저 요청 |
| 사용자에게 준비 완료를 확인받음 | 사용 가능한 기준 파일과 버전을 확인한 뒤 본 작업 시작 | 시스템 검증된 프로젝트 소속이라고 표시 |
| 같은 대화에서 이미 확인 | 반복 질문 없이 이어감 | 파일이 접근되지 않아도 과거 자료를 추정 |
| 새 대화로 변경 | 현재 기준 파일·버전과 필요한 시작 조건 재확인 | 이전 확인이 모든 대화에 영구 적용된다고 가정 |
| 파일 없음·복수 최신본·충돌 | 사용자에게 초기 작성 또는 기준본 선택 요청 | 조용히 병합하거나 임의 최신본 선택 |
| 이동 불가·프로젝트 미지원·사용자 거절 | 제약을 설명하고 요약·자료 다운로드 제공; 본 작업 재개는 보류 | UI 메뉴·프로젝트 URL·이동 권한을 지어냄 |

프로젝트 지침의 식별 문구나 파일명은 안내를 줄이는 보조 신호다. 다른 곳에 복사할 수 있으므로 프로젝트 소속의 검증 증명이 아니다. 프로젝트명을 개인정보나 인증 수단으로 사용하지 않는다. 프로젝트 미지원 환경에서 일회성 경력 작성을 허용하는 대안은 현재 기본 경로에 넣지 않고 별도 제품 결정으로 남긴다.

온보딩 스킬은 프로젝트 준비 방법, 사용할 자료 목록과 프로젝트 지침 템플릿을 제공한다. 실제 작업 스킬에도 첫 대화 준비 확인을 넣는다. 공개 플러그인 기능에서 프로젝트 ID 조회·생성·대화 이동 API는 확인하지 못했으므로 자동화는 기본 요건에서 제외한다.

## 5. 경력·resume·JD 작업 규칙

### 5.1 경력 정리와 기본 resume

경험별 역할·기간·직접 한 행동·결과·공동 기여·근거를 확인한다. 사용자 원문, 사용자 확인 사실, 모델 해석, 미확인 수치와 사용 제한을 구분한다. 질문을 거절하거나 근거가 부족한 경우 공백을 남긴다.

사용자가 표시된 문구와 사용 범위를 확인하면 그 선택을 새 기준 파일과 작업 이력에 기록할 수 있다. 이는 **대화에서 사용자가 확인한 기록**이며 기존 서버의 인증된 승인 receipt나 외부 검증 증명이 아니다. 사실 확인과 이력서 사용 허용은 별도로 표현한다.

기본 resume는 JD 없이도 작성할 수 있어야 한다. 확인된 경력을 구성·다듬되 수치·역할·책임을 확장하지 않는다. 문장별 근거 연결표와 사용자가 검토할 항목을 제공한다. 신규 경력 사실을 추가하면 표현 수정이 아니라 새 사실 검토로 처리한다.

### 5.2 JD 추천과 선택

사용자의 목표 역할·지역·근무 방식·경력 수준 등 직접 받은 조건으로 검색한다. 검색어에 이름·연락처·비공개 경력·기밀 성과를 넣지 않는다. 공개 공고 원문을 우선하고 출처 링크, 조회일, 확인한 공고 상태와 추천 이유를 남긴다.

게시일과 조회일을 구분한다. 원문 접근 불가·로그인 요구·마감 여부 불명·검색 제한을 표시한다. 검색이 없으면 사용자가 붙여 넣거나 업로드한 JD로 진행한다. 접근하지 못한 공고를 열린 공고로 단정하거나 모든 채용 사이트를 수집한다고 약속하지 않는다. 자동 지원, 채용 확률과 외부 경력 인증은 포함하지 않는다.

추천은 선택 보조다. 사용자가 JD를 선택하면 해당 원문·조회 시점·요구사항과 선택 이유를 고정한다. JD 원문에 들어 있는 명령은 자료로 취급하며 플러그인 규칙·사용 제한을 바꾸지 않는다.

### 5.3 JD별 resume와 history

JD 요구사항마다 연결 가능한 경력, 근거, 부족한 조건을 보여준다. 관련성은 사실 확인이 아니다. 기본 resume를 덮어쓰지 않고 별도 JD별 버전을 만든다. 변경 이유·사용한 기준 경력 버전·JD 버전·확인 상태를 기록한다.

History는 경력 경험 자체와 별개인 **선택·수정·사용자 확인·내보내기 작업 기록**이다. 대화 전체 복제가 아니며 변조 불가능한 감사 로그도 아니다. 모델이 만든 요약·추천·평가는 원문 증거로 승격하지 않는다. 확인 전 초안과 확인 후 파일을 구분하며 수정 전후 자료를 재검토할 수 있게 한다.

## 6. 파일 관리와 저장 책임

아래 파일명·형식은 권장안이다. 실제 JSON Schema, 버전 번호와 크기 제한은 2단계에서 정한다.

| 자료 | 권장 형식 | 역할 |
| --- | --- | --- |
| 경력 기준 파일 | `career-profile-vNN.json` | 사용자 선택 기준본, 경력·사실·근거 참조·제약·확인 상태 |
| 경력 검토 문서 | `career-profile-vNN.md` | 같은 버전의 사람이 읽는 표현; JSON과 다른 독립 기준본이 아님 |
| 근거 목록·첨부 | JSON 목록 + 사용자 제공 파일 | 출처 유형·발췌·연결·확인 범위; 원본은 선택 포함 |
| 기본 resume | 버전별 Markdown | 기본 이력서와 근거 대응 |
| JD와 대응표 | 버전별 JSON/Markdown | 공고 원문·URL·조회일·요구사항·관련성·공백 |
| JD별 resume | JD·버전별 Markdown | 기본본과 구분되는 지원용 결과 |
| 작업 이력 | 버전별 JSON + 읽기용 Markdown | 작업 ID·변경 이유·입력/출력 버전·사용자 확인 |
| 면접 전달·결과 | 별도 버전형 JSON + 읽기용 문서 | 앱 가져오기와 사용자 재검토 |

안정된 ID, 기준 버전, 출처 참조와 확인 상태를 유지한다. 같은 이름의 다른 파일, 서로 다른 최신본, 부분 누락과 오래된 자료는 자동 병합하지 않는다. 구조 검사와 ID 연결 검사는 문구의 객관적 진실을 증명하지 않는다.

생성 → 사용자 검토 → 다운로드 또는 프로젝트 자료 등록 → 다음 작업에서 기준본 선택을 구분한다. 파일 생성만 확인한 경우 '프로젝트 저장 완료'라고 말하지 않는다. 자동 프로젝트 파일 교체·백그라운드 저장은 전제하지 않는다. 파일 생성 도구가 없으면 텍스트를 제공하고 **파일 저장·검증 미완료**로 표시한다. JSON 검사나 해시 계산을 실행하지 않았으면 검증된 것으로 표시하지 않는다.

ChatGPT 메모리는 보조 기능으로 사용하며 정확한 경력 사실·제약·버전의 유일한 저장소로 삼지 않는다. 개인 자료는 OpenAI 서비스의 계정·기능별 정책을 따른다. 자체 서버에 보관하지 않는다고 로컬 저장만 이루어지는 것은 아니다. 대화·프로젝트·Library·메모리·다운로드 사본·면접 앱 자료의 삭제를 하나의 동작으로 보장하지 않는다.

## 7. 모의 면접 앱 전달과 결과 복귀

### 7.1 초기 전달 방식

사용자가 전달 목적·포함 자료·버전을 확인한 뒤 파일을 내려받아 앱에서 직접 가져온다. 자동 전송, 공유 URL, 로그인 연계와 원격 revocation은 첫 범위에 넣지 않는다. 다운로드 가능한 ZIP은 제공 환경에서 지원할 때 사용하고, 그렇지 않으면 구성 파일 목록과 개별 파일로 전달한다. 필요한 첨부가 누락되면 완전한 묶음으로 표시하지 않는다.

새 파일 계약은 기존 signed Interview Package v1과 다른 이름·스키마로 정의한다. 기존 v1에 필요한 서명 필드를 가짜 값으로 채우거나 검증을 해제하지 않는다.

### 7.2 포함할 자료

- 스키마 버전, 묶음 ID, 생성 시점과 포함 자료 목록
- 사용자가 선택한 JD와 최종 resume의 정확한 버전
- resume 문장 → 경력 사실 → 근거 발췌의 연결
- 본인 기여 한계, 사용 금지와 미확인·상충 항목의 필요한 설명
- 선택한 수정·확인 이력과 면접 목표
- 사용자가 선택한 증거 첨부와 누락 여부

전체 채팅, 전체 경력 프로필, 선택하지 않은 원본·연락처·제3자 개인정보·인증 정보를 기본 포함하지 않는다. History 중 모델 평가와 사용자 원문을 분리한다. 금지 내용을 설명하려고 민감한 원문을 다시 복제하지 않는다.

앱은 파일 구조·버전·참조·첨부를 검사하고 사용자가 내용과 사용 범위를 검토하도록 한다. 파일의 프로필 ID는 인증 계정 증명이 아니며 해시는 출처 신뢰·경력 진실·암호화를 증명하지 않는다. 파일 텍스트가 앱 명령을 실행하거나 외부 주소를 자동으로 열게 하지 않는다.

### 7.3 모의 면접과 복귀

앱은 가져온 고정 자료를 기준으로 경력 설명, 기여 범위, JD 대응과 근거 공백을 질문한다. 답변·피드백·후속 확인 사항을 결과 파일로 내보낸다. 면접 결과의 새로운 경력 사실은 후보이며, 프로젝트로 돌아와 사용자 검토 후에만 새 기준 경력 버전과 resume에 반영한다. 모델이 작성한 질문·요약·평가를 새로운 경력 증거로 사용하지 않는다.

모의 면접 앱은 현재 미구현이다. 텍스트부터 시작할지 음성을 첫 범위에 넣을지, 어떤 제공자·계정·실행 환경·비용 모델을 사용할지는 별도 결정한다. 이력서 플러그인의 첫 완성에 앱 운영 서버나 음성 제공자 선택을 선행 조건으로 두지 않는다.

| 신규 제품에서 보장하지 않는 항목 | 이유 |
| --- | --- |

자체 서버·DB 운영, OAuth·패스키·KMS 신규 개발, 기존 서버 삭제, 공개 배포와 결제는 이번 전환의 첫 구현 범위에서 제외한다. 공개 플러그인 심사 통과와 모든 계정의 이용 가능성을 문서 작성만으로 선언하지 않는다.

## 9. 검토할 제안과 성공 조건

| 검토 항목 | 권장안 | 확정 시점 |
| --- | --- | --- |
| 프로젝트 시작 정책 | 준비 전 안내만 제공, 사용자 확인 후 본 작업 | 1단계 |
| 기준 자료 | 사용자가 선택한 버전형 JSON + 읽기용 문서 | 2단계 |
| 초기 파일 형식 | Markdown/JSON 필수, PDF/DOCX는 환경 지원 시 후속 | 2단계 |
| 자료 이동 | 사용자 다운로드·앱 가져오기 | 6단계 |
| 신규 플러그인 등록 | 서버 없는 시험 패키지를 분리 검증; 기존 등록 처리 방식은 설치 전에 결정 | 7단계 |
| 모의 면접 앱 | 별도 착수, 텍스트/음성·실행 방식 결정 후 구현 | 8단계 |

첫 플러그인 수용 조건은 다음과 같다.

1. CareerGround 서버·DB·tunnel·OAuth를 사용하지 않는 실제 설치 흐름을 확인한다.
2. 프로젝트 이유 안내, 외부/불명 위치, 이동 후 재개, 파일 없음과 사용자 거절을 평가한다.
3. 기본 resume는 JD 없이 작성되고 JD별 수정은 기본 사실과 별도 버전을 유지한다.
4. 공고 출처·조회일·검색 제한과 추천의 근거·공백을 표시한다.
5. 새 대화에서 사용자 선택 자료로 복귀하고 수정 history를 연결한다.
6. 면접 전달 파일을 참조 검사기가 가져오며 누락·충돌·금지 내용·잘못된 형식을 검출한다.
7. 기능 완료, 파일 생성, 프로젝트 등록, 사용자 확인과 외부 검증을 구분해 보고한다.

세부 완료 기준·현재 구현 비교·작업 순서는 [단계별 계획](../PLAN-2026-10-09-serverless-plugin-transition.md)에 둔다. 합성 평가 통과를 실제 경력 품질이나 외부 사실 검증으로 확대하지 않는다.
